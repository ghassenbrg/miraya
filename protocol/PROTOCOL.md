# Miraya LAN protocol v1

## Optional TV presentation and diagnostic capabilities (0.1.0)

Authenticated `welcome.features` may include `presentation-v1`. Receivers include `display` in welcome/ready and native stats: integer `width`/`height` are the app viewport, `panelWidth`/`panelHeight` the physical display mode, `refreshRate` its Hz, `mode` one of `fit`, `fill`, `stretch`, and `edgeInsetPercent` an integer 0–10 applied symmetrically. These dimensions describe presentation, not encoder/decoder limits. Senders ignore malformed display reports and remain compatible with omitted optional fields.

An authenticated `setPresentation` supplies `mode` and `edgeInsetPercent`. The receiver validates, applies/persists on the UI thread, and replies with `presentation` plus actual `display`. RTP/DTLS/ICE stay intact. Fit contains the whole video; Fill clips inside the inset viewport; Stretch changes proportions. Native stats also publish TV-remote changes.

Native stats additionally expose `videoJitterMs`, cumulative `videoPacketsReceived` / `videoPacketsLost`, and a current normalized decoded `audioPeak`. These are bounded numeric telemetry; audio samples/content are not recorded. The sender computes recent loss from counter deltas. No arbitrary application-launch control is supported; the earlier Netflix handoff experiment was removed at the owner's request.

## Optional direct media (`direct-media-v1`)

Receivers advertise `welcome.features: ["direct-media-v1", ...]`. After authentication, `mediaLoad` starts a separate playback mode, mutually exclusive with live mirror transports. It contains a canonical UUID `loadId`, a `url`, optional media `mime`, finite `volume` 0–1, and up to four explicitly authorized local `assets` (`id` UUID, positive `size` up to 1 TiB). Remote addresses must be HTTPS without URL user credentials. Website pages, blob URLs and arbitrary file/content URIs are unsupported. Nested manifest resources use the same HTTPS-only policy; cross-protocol redirects are disabled.

Local assets use `miraya-file:///<asset-id>` only. The TV requests `mediaRead` with a UUID `request`, authorized asset `id`, nonnegative byte `offset` within its advertised size, and `count` 1–32768. The Mac replies `mediaChunk` with the matching request and base64 `data`, or a generic `error`. These remain bounded control packets inside the existing pinned TLS connection. The Mac holds only user-selected file handles, never accepts a filesystem path from the TV, and revokes them on stop/failure. The receiver allows at most four outstanding requests, bounds chunks, times out reads after eight seconds, and cancels pending reads on close. Seeking issues new bounded range reads; no public listener or plaintext file server is used.

An optional `subtitle` contains an authorized asset URL and `mime` (`text/vtt` or `application/x-subrip`). The TV's Media3 player buffers 15–30 seconds, starts after 1.5 seconds and rebuffers after 3 seconds, subject to its byte/load-control limits. It sends `mediaState` at up to 2 Hz, with `loadId`, `state` (`preparing`, `buffering`, `playing`, `paused`, `ended`), `firstPicture`, `hasVideo`, `positionMs`, `durationMs`, `bufferedMs`, `seekable`, dimensions, rendered/dropped frame counters, rendered audio-buffer count and up to 64 audio/text tracks. Counters describe player output, not physical panel/speaker measurements. Video startup requires first-picture confirmation; audio-only playback can confirm when playing with no video track.

`mediaCommand` requires the active `loadId` and an `action`: `play`, `pause`, `seek` (`positionMs`), `volume` (0–1), or `track` (`kind`: audio/text, `track`: auto/off or reported group:track index). Play after end restarts the item. TV-native controls operate the same player. Existing presentation controls, heartbeat, stop/Back, single-sender authorization and connection deadlines remain in effect. Direct media deliberately does not inherit mirror quality/FPS ceilings or browser overlays. Invalid/protected/unavailable content reports a bounded failure; the Mac does not automatically restart a direct movie from the beginning after a lost connection.

## Core transport

Control transport: a TLS 1.2+ TCP connection, receiver listens on an ephemeral port and advertises `_miraya._tcp.` using DNS-SD. TXT `v=1`, `id=<stable receiver UUID>`. No internet services. Default manual port 7421 (receiver uses this when available). TLS server identity lives in AndroidKeyStore. SHA-256 of DER leaf certificate identifies TV. New pairing uses a fresh six-digit short authentication string with a sender nonce commitment (below). Until verification, TLS is provisional and may carry only pairing metadata/heartbeat controls; no media or saved credentials. Legacy pinned-prefix clients may still verify the first 16 hexadecimal fingerprint characters during TLS and require remote approval. The normal UI exposes only six digits. Following successful approval, sender pins entire certificate fingerprint. Do not advertise certificate fingerprint. TV must separately approve unknown senders with remote. Tokens are random 32-byte base64url secrets, stored privately on receiver, Keychain on Mac. Never log tokens. Known UUID alone is not authentication. Clearing trusted Macs revokes all tokens. Unknown clients rate limited and approval expires in 30s. One active sender at a time. TLS handshake/read deadlines and bounded clients required.

Every packet has a 24-byte big-endian header: magic 4 bytes ASCII MRY1; type UInt8; flags UInt8; reserved UInt16=0; payload length UInt32; presentation time UInt64 microseconds (valid range 0...Int64.max; high bit must be zero for cross-platform clock arithmetic); sequence UInt32. Maximum payload 4 MiB, control/config max 64 KiB. Reject invalid magic, flags other than bit0 on video, reserved, length, type. Sequence increments per outgoing direction, starts at 0; diagnostic only. pts is sender monotonic media timestamp, same clock for video/audio (CMSampleBuffer presentation time microseconds). Control pts=0.

Types: 1 UTF-8 JSON control object, 2 UTF-8 JSON video config, 3 H.264 Annex B access unit, 4 signed PCM16LE interleaved stereo 48000Hz. Video flags bit0=IDR. Config SPS/PPS are base64 **raw** NAL units without start codes. Config always precedes first video and each encoder recreation. Audio max 19200 bytes per packet (100ms), no microphone. Both sides ignore unknown JSON keys, reject unknown required op/version.

Handshake sender -> `{"op":"hello","version":1,"clientId":"UUID","name":"Mac name","token":"optional secret"}`.
Receiver -> `{"op":"pending"}` when waiting for TV approval; then `{"op":"welcome","version":1,"receiverId":"UUID","name":"TV name","token":"secret","maxWidth":1920,"maxHeight":1080}` or `{"op":"error","code":"denied|busy|auth|version|timeout|protocol|decoder","message":"human readable"}` followed by close. Known client with invalid token fails; never silently re-pair. New pairing only with foreground TV approval. Welcome token is sent for both known and newly approved client.

For new short-code pairing, hello additionally contains `"pairing":"sas6-v1","commitment":"64 lowercase hex"`. The commitment is SHA-256 of UTF-8 `"Miraya sender commitment v1\n" + senderNonce`; nonce is 32 random bytes encoded as 64 lowercase hex. Receiver fixes its TLS certificate before hello, then replies `{"op":"pairChallenge","pairing":"sas6-v1","nonce":"64 lowercase hex"}` with a fresh receiver nonce. Sender replies `{"op":"pairReveal","nonce":"sender nonce"}`. Receiver validates the commitment before displaying a code. Both SHA-256 the UTF-8 newline-separated sequence `Miraya pairing SAS v1`, lowercase full certificate fingerprint, lowercase client UUID, sender nonce, receiver nonce (no final newline). Interpret the first four digest bytes as unsigned big-endian, modulo 1,000,000, formatted as exactly six decimal digits including leading zeroes. Receiver sends `{"op":"pending","stage":"code","expiresIn":90}`; the code itself is not transmitted. User compares the screens; Mac locally confirms and sends `{"op":"pairConfirm"}`. Receiver clears the displayed code, sends `{"op":"pending","stage":"approval"}`, and requests TV remote approval. Only then can welcome/token storage and media follow. Unexpected/repeated challenge, wrong reveal, downgrade, early welcome/media or timeout fails closed. Saved pin/token connections skip this exchange. Shared vector: fingerprint `ab` repeated 32, UUID `12345678-1234-1234-1234-123456789abc`, sender nonce `01` repeated 32 and receiver nonce `02` repeated 32 produce **447474**.

## Native UDP media (current apps)

Welcome advertises `"transports":["webrtc-udp-v1","tcp-v1"]`. Current Mac apps require `webrtc-udp-v1` and fail with an update instruction for older TVs. Start includes `"transport":"webrtc-udp-v1"`, audio and volume. Ready includes that transport and a fresh UUID `session`. The authenticated TLS channel carries `rtcOffer`/`rtcAnswer` with `session` and `sdp`, and `rtcCandidate` with `session`, `candidate`, `mid`, `index`. Every signal must match the active media session. Reject pre-start signaling, SDP over 32768 UTF-8 bytes, non-audio/video media, missing SHA-256 DTLS fingerprint/ICE credentials, and non-UDP/non-host candidates (including inline SDP candidates). Candidates are capped at 4096 bytes and a 64-entry pre-description queue. Native parsers also validate SDP/DTLS.

Media uses native RTP/RTCP over UDP with ICE and DTLS-SRTP, H.264 VideoToolbox on Mac, Android's decoder factory/Surface renderer, and stereo 48kHz Opus capped at 192kbit/s. No data channel, external ICE servers, TCP candidates, or cloud relay. Mac advertises H.264 level 4.2; Android raises its generic level-3.1 declaration only within platform-reported decoder limits. Sender adapts source dimensions/frame rate to the receiving level. The native screen source enables application-limited bandwidth probes, a pacing factor of 1.5 and a 200ms pacer queue allowance using pinned M150's `WebRTC-ProbingScreenshareBwe` configuration. Explicit quality/resume changes remove stale quality-scaler resource restrictions before restoring frame-rate priority. A hysteretic quality probe can retry larger dimensions after capacity recovers. Native congestion/loss recovery governs bitrate, resolution, retransmissions and keyframes. That queue setting does not bound total network/decoder/display delay.

Capture timestamps share the Mac host clock. The input-only custom audio device accepts captured PCM, retaining at most 60ms and producing 10ms blocks with capture host timestamps; it never opens a microphone. The documented render-block input path avoids M150's direct-buffer stereo span truncation. Integration diagnostics require near-real-time audio packet/sample progression, not only a playing AudioTrack. Sparse repeats of the most recent complete screen buffer permit loss recovery on a static desktop. Pause stops capture and disables tracks; resume/reconfigure retain the same peer UUID, DTLS and ICE, with a fresh source when needed. Audio focus, enable and gain remain receiver controls. Native counters are cumulative through live controls. Sender playback-capacity feedback separately bounds decoder/render load: sessions start at up to 30fps and probe a 60fps maximum once after five healthy seconds of moving input; active-input drops lower it back to 30fps, then reduce dimensions if 30fps remains overloaded. Changes have a cooldown; static/paused input does not downgrade, pause retains learned capacity, and explicit quality changes retry it. Native sessions reject legacy config/video/audio packets over TLS. A failed/disconnected peer has bounded recovery; an encoder that receives frames but makes no progress for eight seconds fails into the normal bounded reconnect flow. Ready and offer negotiation also have deadlines. Sender presentation progress is checked separately from encoding: eight seconds without a rendered-frame increment while video input is active invokes bounded reconnect, even if TLS heartbeats and ICE remain alive. Static cached repeats make real idle distinct from a stalled receiver.

Native stats additionally report `transport`, `protocol`, `decoded`, `videoCodec`, `audioCodec`, `videoWidth`, `videoHeight`, `rttMs`, `jitterMs`, playback options, `audioPlaying`, `audioSignal`. `frames` counts EGL renderer callbacks, not camera-observed TV presentation. `audioFramesWritten` and the compatibility `audioFrames` count PCM offered for native AudioTrack playout, not a physical speaker measurement. `audioSignal` records observed non-silent decoded PCM; `audioStereoSignal` observes differing decoded left/right samples during the generated stereo test. Native `lastPts`/`lastDecodedPts` are -1: RTP clocks must not be compared directly with legacy microsecond PTS. Mac reports native encoder dimensions/FPS/quality limit, target bitrate and nominated candidate-pair estimates. Network RTT is not glass-to-glass latency.

## Legacy TLS media (compatibility and diagnostics)

Without a transport field, the receiver retains `tcp-v1` for older clients and existing fixtures. The following queue, framing, PTS, playout and codec rules apply only to that legacy path.

After welcome, sender sends `{"op":"start","audio":true|false,"volume":0.0...1.0}`; receiver -> `{"op":"ready"}` when surface is available and stream may begin. Video config: `{"width":1920,"height":1080,"fps":30,"sps":"base64","pps":"base64"}`. Decoder renders letterboxed, never stretches. Receiver can return `{"op":"requestKeyframe"}` after dropping decoder backlog. Sender may skip capture before encoding under pressure. When dropping already encoded, unsent video, it must also discard dependent video until the next IDR; preserve control/config order. Keep the TLS session and recover with an IDR for transient congestion. Discard queued media older than 200ms; bound normal pending media to 512KB, allowing one valid IDR up to the wire limit. The packet already handed to TCP cannot be withdrawn. Sequence gaps from discarding unsent packets are valid.

Receiver drops input until the next IDR when overloaded, retains any pending configuration and an arriving IDR, and flushes the running decoder with codec parameter sets resubmitted. Only an actual configuration change recreates the decoder. Video uses a 40ms initial playout target and re-anchors after a clock slip greater than 100ms late or 200ms early. A stale/underrun audio clock must not block video. Audio queued more than 120ms behind newer received audio is skipped.

Receiver sends `{"op":"stats","frames":N,"dropped":N,"lastPts":N,"lastDecodedPts":N,"recoveries":N,"audioFrames":N,"audioFramesWritten":N}` every 250ms while streaming. `lastPts` is the most recent scheduled video timestamp, `lastDecodedPts` the greatest decoded timestamp including output discarded for presentation (-1 before output), `recoveries` counts backlog/input recovery events, `audioFrames` is the AudioTrack playback head, and counts are cumulative per session. All telemetry fields are optional. Sender prefers decoded progress and falls back to `lastPts` for older receivers. TCP send completion alone does not prove playback progress. More than 400ms of timestamp backlog or 700ms without progress throttles video with a recovery opportunity every 250ms, rather than stopping it completely. Persistent backlog and local write pressure reduce bitrate and request an IDR. Eight seconds of outstanding video without any decode progress, or a single socket write stuck for eight seconds, triggers reconnect. When the desktop is static and all video is acknowledged, no playback stall is outstanding; the next frame starts a fresh progress deadline.

While streaming, `{"op":"setVolume","volume":0.0...1.0}` immediately changes Miraya's AudioTrack gain (finite values only), without changing device master volume. `{"op":"pause"}` stops receiver media and releases audio focus; receiver replies `{"op":"paused"}`. Sender stops capture before sending pause. TLS/heartbeats remain alive; reset the sender's outstanding-media watchdog on paused. `{"op":"resume","audio":true|false,"volume":N}` recreates media and replies ready; `{"op":"reconfigure",...}` does the same during playback for quality/audio changes. Sender stops old capture first and starts fresh capture/configuration only after ready. Frame counters restart with the media pipeline; trust/session stay intact. An enabled audio setting on resume reacquires focus. Paused capture may change display. Back/stop remains final.

Either side can send `{"op":"ping","nonce":N}` every 2s; peer replies pong same nonce. 10s without incoming data terminates session. Sender sends stop on user stop, receiver sends stopped then closes session; receiver remote Back sends stopped then closes. Unexpected disconnect ends capture; Mac may retry known TV for up to three attempts, but must clearly show reconnecting and stop when cancelled. Never resume after explicit TV stop/denial. A newly authenticated connection must send start before media.

Scope: macOS 13+, Android TV API 26+, SDR H.264 8-bit 4:2:0, maximum 1920x1080 at 30/60 fps (720p mode for weak networks), system audio optional. Receiver limits actual support with MediaCodec; unsupported stream returns useful error. No cloud, Bluetooth, remote input, DRM bypass, UPnP or port forwarding.
